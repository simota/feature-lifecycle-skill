Agent Skill / one feature, discovery → ship

Feature LifecycleFrom an unstated need to a released change. One invocation, one feature.

Nine phases, ten gates, three engine roles. Every phase emits a typed artifact and every boundary has a named gate. A failed gate returns to the phase that caused it — never forward with a note attached. The chain is expensive on purpose: the cheapest place to find out you built the wrong thing is before you build it.

01The chain, including the way back

Anyone can draw the forward path. What this figure exists to show is the return edges — where a split verdict, a No-Go risk gate, and a gap found by the acceptance verification each send the work. A phase advances only on its declared exit criterion; every other road leads upstream.

Convergence is not correctness. A loop that stops producing changes has only proven that it passes its own tests. What guards Ship is the independent acceptance verification, never the loop's own exit reason.

02When this is the right chain

Feature Lifecycle is opt-in, never a default. It is for the case where an upstream gap — a missed user need, a weak spec, a hidden architecture risk, UX friction — is materially costly to discover after implementation. When that is not true, a lighter chain is the correct chain.

Use it when at least 3 apply

  • New customer-facing feature with a UI surface — not a backend-only fix
  • Cross-team impact: business, engineering and design
  • Reversibility cost is high — DB migration, API contract change, brand-visible UX
  • Acceptance criteria are not pre-supplied and must be derived from user need
  • An architecture decision is required, not just an implementation
  • 5+ files / 2+ modules / 2+ days estimated

Route elsewhere when it is

  • A defect in shipped behavior — diagnose and fix, no discovery chain
  • One bounded capability whose shape is already settled — a single guided build
  • Spec and acceptance criteria only, no code
  • Decomposition and sequencing only, no execution
  • Design exploration without implementation
  • Executing a pre-authored multi-package plan
  • A behavior-preserving rewrite or port, where the oracle is the old behavior
  • Improving one already-correct slow layer against a number

03Modes and dispatch

The default mode is AUTORUN_FULL. There is exactly one human checkpoint — the Phase 0 boundary confirm. Downstream, only an internal gate, the loop circuit breaker, the engine-availability check, or the budget ceiling stops the run.

Subcommands

feature-lifecycle <description>  # goal supplied → Phase 1
feature-lifecycle                # autonomous → Phase 0
feature-lifecycle bootstrap      # explicit form (alias: auto)
feature-lifecycle resume         # from the last checkpoint

# optional arguments
scope=Lite|Standard|Full  ui=  api_change=
db_change=  budget=

A bare invocation with a resumable checkpoint present never picks silently. It names the checkpoint and asks which — resume it, or start a fresh bootstrap. Resuming the wrong run and re-deriving a finished one cost the same as each other's mistake.

05Phase 6 — the per-cycle spawn sequence

The loop is where maker ≠ checker has to hold. Implementation on build, review and tests on judge, long-flow E2E on breadth. The vertical jumps between lanes are the mechanism: a test written on the same engine that wrote the code is the nodding loop with an extra step.

The iteration ceiling is keyed to the build engine

build engineCeilingWhy
Codex CLI≤ 6The default the cost profile is written against
agy≤ 6Code-gen throughput is lower, so a cycle achieves less — the run needs the headroom, not less of it. What changes is the budget envelope, recomputed at agy's rates, never the safety bound
Claude Code≤ 4Context isolation is weaker: in-loop spawns share a main session that accumulates rot, so drift arrives earlier in the cycle count. The tighter bound is about isolation, not speed
A lower ceiling is not a penalty for a slower engine. Confusing the two produces the exact wrong move — cutting cycles from the engine that needs more of them.

06Why the verification is two-sided

Conformance alone is a one-sided test. An implementation can satisfy every AC and have grown a feature nobody asked for, a dependency nobody approved, or a table nobody specified. An autonomous loop is exactly the setting where that happens, because "add a little more" always looks like progress from inside the loop.

Conformance — was the spec built?

Extract the L3 ACs, adversarially check the delivered implementation, emit a traceability matrix of AC → evidence → verdict.

conformance ≥ threshold · unmet_must_haves == 0

Negative pass — was only the spec built?

Walk non_goals and the Phase 3 scope boundary against the actual diff: new surfaces, new dependencies, new config, new persisted state, behavior outside the declared boundary.

non_goal_violations == 0 — every out-of-boundary change is either reverted or explicitly ratified by the user, never silently kept.

Independence here is model independence, not merely context independence. A fresh context on the same model carries the same blind spot into the room that was convened to find it. So the verification runs on judge, and never on the engine that built — wherever a second engine is reachable. Where only one was, the pass still runs and the Delivery Report records engine_independence: context-only rather than implying a guarantee the run did not have.

Integration evidence — a conditional third pass

ConditionAction
An integration surface exists and is reachable — a preview environment, a staging deploy, a policy or attestation checkRun the must-have ACs against it; record integration_evidence: E5 and any AC the real surface failed
No such surface existsRecord integration_evidence: unavailable with what would have to exist

Findings here do not block the exit gate on their own — an unreachable staging environment is not the run's fault. An AC that passes locally and fails on the real surface does block: that is a conformance failure the local oracle missed, and it re-enters Phase 6 like any other.

07The engine roster

A role is a property of the work, not a brand loyalty. The defaults are bindings, not identities: a probe that cannot reach the default rebinds the role and records it. Nothing downstream reads a CLI name; everything reads the role. The probe runs once, before the first spawn, and is cached for the run.

Hard rules

  1. acceptance-verification.engine ≠ build.engine, wherever a second engine is reachable. With one, the verification still runs and is recorded as context-only.
  2. Phase 3 runs one voice per distinct engine. With three reachable: logic = judge, human-impact = breadth, precedent = build.
  3. No silent rebinding. A role bound to something other than its default is recorded at bind time and named in the Delivery Report. The cost and convergence model is scored against a named roster.
  4. The hub never delegates orchestration. Gates, checkpoints, the budget ledger and the Delivery Report stay on the hub whatever the roster resolves to.
  5. Degradation changes who runs a gate, never whether it passes. No threshold moves because an engine was missing.
"Present but unusable" is not "absent". A binary that answers but whose role spawn fails on auth, quota or config is a transient blocker. It is surfaced through the degradation protocol's abort-and-resume option — Phase 0–5 output is already checkpointed — not silently rebound. A blocker resolved in ten minutes is cheaper than a run scored against the wrong roster.

09What a run leaves behind

The Delivery Report is a summary. It quotes a traceability percentage, a Risk-Gate verdict and a conformance number, and carries none of what they were computed from — the personas that produced no usable demand, the FMEA rows below the RPN threshold, the architecture the ADR rejected, the reuse scan's near-misses. Each is produced by an expensive phase, read once by the next phase, and then gone. So every run writes a run record to .agents/feature-lifecycle/runs/<run-id>/, opened before the first spawn and committed with the change it describes. In autonomous mode those two demands collide — Phase 0's scan spawns before a goal exists to name the directory after — so the id is two-stage: a provisional YYYY-MM-DD-bootstrap-<n> at launch, renamed once to the goal slug at the boundary confirm, before Phase 1 opens.

The file number is the phase number. A phase that did not run has no document; a conditional row that did not run is a line in its phase's document — "the UX track did not run, there is no UI surface" is a finding, a gap in the numbering is a puzzle.

Four sections, every phase

Quoting the criterion rather than paraphrasing is what makes the record auditable: a gate written down as "traceability OK" cannot be checked against a threshold that was 85%.

The journal stays a journal. Before the run record existed, a run with something worth preserving had nowhere to put it but the journal — which is how a learnings file becomes a diary nobody reads.

What never goes in. Secrets, tokens or customer data — the record is committed, so treat every line as published, because it is. Raw spawn transcripts — the store is analysis, and a producer's own reasoning trace is E0 on the evidence ladder, not evidence for anything the record claims. The diff — git holds that; the record names the files and the reason. And a number with no source: a conformance percentage or an RPN is written with what produced it, because the run record is not the place to add confidence the run did not earn.

10Cost, budget and resume

The agent counts are engine-agnostic; the cost is not. A run spread across three CLIs spends against three pricing models, so the envelope carries a per-engine sub-ledger and a single mixed total is never quoted as the figure.

ProfileAgentsCost
Lite — no UI, spec scope Lite11–13Low

Counting loop iterations, that is 27–61 spawns at the Full autonomous profile. For repeated similar requests, propose a project-local skill to amortise the chain design cost instead of re-running the chain.

The budget envelope

  • Declared at launch. Default ceiling = the cost-profile estimate × 1.5; the user may override.
  • A warning at 80%. GUIDED/INTERACTIVE pause for a continue/abort decision; AUTORUN_FULL logs and proceeds to the ceiling.
  • The ceiling is a hard stop, not advisory. It is what protects against a runaway Phase 6 loop or a re-entry storm from the acceptance gate.

Checkpoint and resume

The Phase 0 goal artifact, the Phase 3 verdict + AC seed, the Phase 4 spec + traceability, the Phase 5 design + Risk-Gate result, and the Phase 6 build state are each persisted as a resumable checkpoint. A run that aborts mid-flight resumes from the last good phase instead of restarting from Phase 1 — so a runner problem never costs five completed phases. resume reads RUN.md and re-binds the artifacts it names (§ 9); it never infers the resume point by scanning the directory, because a listing cannot tell a sealed phase from one killed a second before its gate.

The Delivery Report is emitted on every exit, aborts included. Budget ceiling, Risk-Gate No-Go, an acceptance failure past the re-entry cap, an unavailable engine with no answer — each still emits, with best-so-far per phase, the residual gap, and the resumable checkpoint. Never a silent stop.

11Gotchas

Each of these is a run that passes its gates and is wrong anyway. They are the reason the chain is expensive.

  1. A loop that converges is not a loop that is correct. Convergence means the iteration stopped producing changes; it can stop on an implementation that passes its own tests and misses the spec entirely.
  2. Conformance alone is a one-sided test. An implementation can satisfy every AC and have grown a surface, a dependency or a table nobody specified. The negative pass is what makes the scope boundary load-bearing rather than decorative.
  3. An upstream packet collapses derivation, not verification. Arriving from a spec packet means Phases 1–4 become validation — not that the Risk Gate or the acceptance verification get lighter.
  4. Three seats on one model is not a tri-engine verdict. Phase 3's cost is justified by three engines actually disagreeing; a single model arguing with itself converges on its own priors and returns a confident split that means nothing.
  5. Conformance is not validity. The verification proves the spec was built; it is silent on whether the demand the spec came from existed. That is why the measurement contract leaves the run open rather than closed.
  6. A silent runner swap invalidates the run's cost figures. Iteration ceilings and budget envelopes are scored against one named engine. A fallback nobody was told about produces numbers that read against the wrong model.
  7. A clone's declared parity ceiling is a constraint, not a defect. A loop given a parity harness will happily "fix" a ceiling-bound behavior and move the product off its baseline.
  8. Phase 1 on an existing repo means a reuse scan first. A second implementation of something the repo already ships is discovered in Phase 1 for the cost of a scan, or in Phase 6 for the cost of the whole loop.
  9. The next Phase 0 goes blind. A feature shipped without the events behind its own measurement contract is invisible to the following autonomous scan — and the blind spot compounds fastest on exactly the features the loop was most confident about.
